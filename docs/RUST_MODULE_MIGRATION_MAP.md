# HRFlow Rust module migration map

**“All HRFlow modules” means feature parity for every product destination and nested workflow in the production PWA, with the separate Android client brought to parity as an explicitly chosen client target.** It does not mean the current Rust pilots are production modules: today the React PWA remains live, the Dioxus attendance screen is synthetic, and the Kotlin app is an authentication/profile foundation. The map below is grounded in PWA baseline `origin/main` at `c191ae98a8789e1b5cb93edcd904182ceb8f36e2` (2026-10-02); PWA source paths in this document are relative to that repository and commit.

## Is the architecture sound?

**Yes as a safe migration architecture; not yet as a completed end-state design.** Isolated Rust domain crates behind explicit client boundaries let the team prove business-rule parity without moving production callers, Firebase, security rules, data, or offline behavior. The existing workspace enforces a prototype-UI-to-pure-domain direction and correctly avoids empty infrastructure layers. Its current evidence—18 numeric attendance-grace vectors, 27 leave-entitlement fixture comparisons, and a synthetic read-only Dioxus attendance workflow—is useful pilot evidence, not production feature migration.

To satisfy a literal “all screens authored in Rust” goal, a later client phase still has to choose how the web/PWA and Android interfaces will be built and connected to platform services. The current PWA uses Firebase’s JavaScript client, Firestore IndexedDB persistence, service-worker/update and push behavior; Android has Kotlin/Compose adapters for Firebase Auth and a profile listener. Keep those official platform SDKs behind thin JS and/or Kotlin adapters unless the product explicitly chooses a different data/API strategy. Do not move credentials, tokens, or broad employee records into WASM, use client UI permissions as authorization, or change schemas/rules as an incidental part of the port.

The remaining material architecture choice is Android UI ownership: retain Compose and call shared Rust domain code through a narrow Kotlin/native boundary, or evaluate a Rust-authored Dioxus Android UI and its WebView/platform bridge. The prototype has a two-ABI **unsigned package** proof, but no Android runtime, Firebase integration, network permission, device, or accessibility proof; it does not settle that choice. The web deployment/PWA path also needs an explicit decision because Vite service-worker behavior, offline cache, push, PDF/CSV exports, and current Hosting/Vercel setup are part of the product, not incidental packaging.

## What is in production today

`src/App.jsx` declares `/login`, protected `/`, and protected `/mobile`; `/tasks` and `/tasks/checklist` redirect into Dashboard tab/query state, and unknown paths return to `/`. Signed-in users on mobile are redirected to `/mobile`. `src/pages/Dashboard.jsx` registers the desktop destinations and dispatches them to feature components; `src/components/MobileDashboard.jsx` has a separate mobile module list and render switch. Desktop hides `chat` from its sidebar and URL-tab allow-list, but mobile registers Team Chat. Destinations are permission-filtered in the UI; this is not a complete list of all component files, nor is UI permission filtering server-side authorization.

## Suggested sequence and release gates

1. **Freeze the source contract and settle client strategy.** Keep `c191ae98…` as the PWA parity oracle; enumerate the concrete route/subtab behavior, Firestore document shapes, error/empty states, and platform dependencies. Decide whether Android is Rust-authored UI or Kotlin/Compose over shared Rust domain code, whether the existing Firebase client read/write model remains, and which web/PWA deployment and offline semantics are contractual. No live data or rules changes are part of this phase.
2. **Finish bounded pure-domain evidence.** Expand the existing attendance and leave fixtures from representative vectors to observed caller/persisted-data shapes, including coercion/date/time boundaries. Benchmark JavaScript vs WASM on representative workloads, including WASM loading/call overhead. Keep production JS behavior authoritative; the existing Dioxus screen stays synthetic until real adapters and parity gates exist.
3. **Build identity, organization and employee read adapters.** Define narrow typed boundary DTOs and preserve current Auth/organization behavior; prove tenant/cache isolation and access checks in a safe test environment before any live reads. Establish bounded employee queries and then deliver the first non-mutating Rust-authored directory/dashboard/report slices. Do not move authorization into the UI or widen data reads.
4. **Migrate independent read surfaces, then bounded writes.** Add read-only module slices against the established adapters; then migrate independent task/engagement or recruitment writes in separately reversible units with authorization, immutable audit behavior, duplicate/retry handling, and observable rollback. File transfer, broadcasting, profile changes, and financial writes remain distinct higher-risk boundaries.
5. **Migrate Leave and Attendance as a coordinated state machine.** Port pure rules first, then preserve coverage, correction, OT, approval, audit, payroll-lock, batch/transaction and conflict behavior across both modules. Do not switch either production write path while the other can still violate the shared invariant.
6. **Migrate compensation inputs and Payroll in dependency order.** Characterize finance claims, allowances, fines and loans first because payroll consumes them; port calculation and snapshots; then prove payroll lock/reopen interactions with attendance and leave. Treat payslip reads, generation, export and writes as separate parity checks. A payroll cutover is the last financial gate, not a test of the calculation function alone.
7. **Complete higher-sensitivity and platform-heavy surfaces.** Bring recruitment/onboarding, documents/Storage, communications/distribution, settings/role workflows, fleet, chat, exports and push to parity in bounded slices. Settings policy writes should follow the consumers whose behavior they configure. Finish web/PWA install/offline/update and Android runtime/accessibility proof before declaring cross-client completion.

**A module is not “migrated” merely because Rust code exists or a screen renders.** Before a production read or write switch, each module must pass: (1) functional parity against representative fixtures and the source application, including loading/empty/error/recovery paths; (2) org/role/employee isolation, authorization and audit checks at the actual Firebase boundary; (3) offline/cache/reconnect behavior and PII/export/storage privacy; (4) mobile layout, keyboard and assistive-technology checks; (5) measured startup, bundle/WASM size, query cost and representative latency against the current client; and (6) a tested rollback path with the old implementation available. A write workflow also needs idempotency/retry, transaction/batch limits, and before/after persisted-state comparison. Until all applicable gates pass, keep the old client authoritative and do not enable dual writes or silently change data/security configuration.

## Decisions still needed

- **Android presentation:** Dioxus-authored screen/runtime vs Compose screens that share Rust domain crates. This determines whether the native project remains a client to migrate or is eventually replaced.
- **Data/API boundary:** retain direct Firebase client reads/writes behind JS/Kotlin SDK adapters, or separately design an API/service boundary. A service would change authorization, offline/listener behavior and operations; it is not implied by the Rust pilot.
- **Web/PWA release contract:** preserve the current Vite/service-worker, Firestore cache, push, PDF/CSV, Capacitor updater and deployment behavior, or replace any of them only through an explicit product decision and parity plan.

Until these choices are made, the architecture is sound for the current reversible pilot but cannot honestly be described as a complete architecture or migration of all HRFlow modules.


**Access-boundary caveat:** In the inspected PWA commit, `firestore.rules` permits signed-in reads of top-level user/organization documents and generic organization subcollections; organization writes are based on active-organization fields or `adminUids`, not the UI module-permission map. `storage.rules` similarly authorizes broad organization/request prefixes. This is a source-code observation, not verification of deployed Firebase configuration. The rules were not changed here. A Rust screen or adapter must not claim stronger server-side isolation than those rules provide; validate the required access boundary before enabling any new live path. Any rule tightening is a separately scoped, explicitly approved change, and rules must never be weakened as part of this migration.
