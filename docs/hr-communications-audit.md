## Current behavior and gaps

| Subtab | Before this pass | Main gap confirmed |
|---|---|---|
| **Letters** | HR could create a draft for one employee and issue it; issuing created a reference number and an employee-inbox copy. Letter types and an effective date were stored, but draft editing and deletion were absent from this workspace. | The model already included `pending_approval` and `approved` states, but the screen did not provide a real request/review transition. Issued copies needed to remain immutable. |
| **Announcements** | Drafts supported category, audience (`all_active`, site, or department), priority, and seen-versus-acknowledged response mode. Publishing resolved the audience and wrote a delivery snapshot per active employee. | The UI did not show a recipient preview, editable expiry, reliable read tracking, or useful delivery-response totals. Publishing errors were presented through browser alerts. |
| **SOPs & Policies** | Policy drafts had document codes and stored effective and review dates; the helper already supported versions and publishing created employee delivery snapshots. | Dates were not all exposed in the form, published records had no revision workflow, and approval states were not interactive. Changing policy text in place would risk confusing the current version with copies already issued. |
| **Training** | HR could create a programme invitation with category, session date, delivery mode, and audience, then publish it to employees. | Response tracking was not surfaced in the detail view. The workflow is invitations and acknowledgements—not a learning-management system with course completion. |
| **Templates** | HR could create a reusable named text template and type; the record had a version field. | There were no edit or delete controls, version changes were not meaningful, and the screen did not explain that it did not expand dynamic placeholders. |
| **Archive** | The tab combined the four communication collections, but had no dedicated archived-state filter. Its Withdraw button passed the synthetic `archive` tab id into a mutation function that only accepts the real communication kinds, so that action could silently do nothing. | Users could not reliably distinguish historical items, expired records, and live records, or understand which historical items remained editable. |

The data already lived in organisation-scoped `letters`, `announcements`, `policy_documents`, `training_programmes`, `communication_templates`, and `communication_deliveries` collections, with a separate `communication_audit` stream. The employee inbox read delivery snapshots rather than live source text, which is the right basis for preserving what an employee actually received. The permission helper, however, treated create/edit/approve as interchangeable for management actions, and ownership fields were not consistently written for all newer records. These are application-level controls only: the existing audit notes that Firestore’s broad organisation read rules do not enforce this UI permission model. No Firestore security rules were changed in this pass.

## Improvements made

The landing view now explains the purpose of HR Communications and the draft → review → publish/issue → response path before the user chooses a subtab. Each subtab has concise, task-specific guidance; list search covers names, titles, employee, category, and document code; empty states distinguish “nothing exists” from “no matches”; forms validate required fields inline; and audience-driven forms preview the number of active recipients using actual site and department values. Primary forms follow the repository’s shared input sizing and blue design tokens.

HR can now edit its own drafts and templates, while admins can manage records across owners; deletion is limited to drafts and templates, confirmed in context, and never removes employee delivery snapshots. Create, edit, delete, approve, publish, issue, withdrawal, and employee-response operations write the existing communication audit entry and an organisation-level `audit_logs` entry. Approval is now real: an authorized creator/editor can request review, an authorized approver can approve, and only then can the item be issued or published. Publishing and issuing show the exact title, audience, version, response requirement, and relevant dates before confirmation. A published or issued item cannot be edited in place.

Policy updates use a new revision draft rather than overwriting a published version. The new version carries the document code and audience forward, increments the version, and points to the prior version. On publishing the replacement, the prior version is marked superseded; its delivered snapshots stay in HR history but are no longer shown as active in the employee inbox. Announcements can now carry an expiry date, and policy/announcement forms expose acknowledgement behavior. Date-only expiry remains active through the selected calendar day, disappears from active employee inboxes afterward, and remains searchable in HR history. Effective and review dates are clearly displayed; an effective date is not a scheduled-publishing control.

Employee inbox opens now mark ordinary “seen” deliveries as seen, while acknowledgement-required items remain pending until the employee explicitly confirms. HR detail views show aggregate acknowledged/seen/pending totals. Withdrawal hides the content from active employee inboxes without erasing delivery or acknowledgement history. The Archive view is a searchable, status-filtered history across existing collections; it is not a new storage collection. The excluded **Formats** workspace and its existing route were left unchanged.

## Remaining limitations and verification

Firestore and Storage authorization were intentionally left untouched. The UI and hooks now check action capability and owner for draft/template edit and delete, but client checks do not secure direct Firestore reads or writes; the existing broad Firestore rules remain the actual boundary. The new approval flow has request and approve states but no reject/return-to-draft action, no dedicated reviewer queue, and no automatic approver notification. Publication is immediate: there is no scheduler, review-date reminder, expiry job, or external notification; expiry is applied when evaluating employee inbox visibility and when filtering HR history. HR sees aggregate response totals, not a per-employee acknowledgement register or export.

Training remains invitation-and-acknowledgement only. Templates store reusable text and increment a version on edit, but do not expand placeholders or generate signed documents. Letters remain employee-specific text snapshots rather than downloadable files. No legal or statutory policy language was inferred or changed.

Verification passed: `npm run test:communications` (7 tests), `npm run test:leave` (7 regression tests), focused ESLint across every changed JavaScript file, `git diff --check`, and `npm run build`. The production build still reports repository-level warnings for stale Browserslist data, unresolved font references, an unsupported CSS property, and JavaScript chunks over 1 MB. No Firestore rules changed, and the separate employee-modal worktree remains untouched.
