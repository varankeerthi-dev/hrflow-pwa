HRFlow already covers a substantial HR lifecycle: employee records and self-service, attendance, leave, shifts, payroll and payslips, recruitment, HR communications, documents, training, approvals, and employee engagement. The audit finds that several workflows are complete enough to use, while statutory payroll, onboarding/offboarding, privacy boundaries, and a few policy and engagement interactions remain incomplete or need validation.

## UI/UX audit and changes made

The app has two useful but distinct navigation models: desktop groups HR and management modules in a sidebar, while mobile presents categorized tiles. Before this pass those registries diverged: mobile had a Recruitment content switch but no Recruitment tile, had neither an Employees tile nor an Employees render case, and desktop omitted the existing Shift Planning view. The branch adds mobile Employees and Recruitment entries and their route, and places the existing Shift Planning component in desktop management navigation. Shift permissions recognize both the canonical `Shifts` key used in the application permission model and the older `ShiftPlanning` key, without granting access to users who had neither permission.

The employee detail panel previously printed Aadhaar, PAN, account number, and IFSC in clear text. These values now display masked by default, preserving the final four characters for quick identification; a keyboard-operable button with a changing accessible name and pressed state deliberately reveals or re-masks them. Reveal state is keyed to the selected employee, so changing records does not carry the prior employee’s reveal state forward. Existing employee detail fields, activity navigation, and leave, attendance, fines, advances/expenses, and variable-pay summaries remain available. This is a presentation safeguard only: anyone who can already open employee details can still reveal the values, and security rules must be addressed separately.

Other confirmed friction points are less urgent but worth attention. `EmployeesTab.jsx` uses its own teal visual system while the repository design reference (`NEW_DESIGN_SYSTEM.md`) specifies blue as the primary brand color; the mobile dashboard and desktop sidebar also use different tile/row patterns. This is not a reason to force a risky redesign, but shared navigation and form primitives would make the experience more consistent. The existing attendance-policy editor is saved and rendered in `SettingsTab.jsx`, and its data model is in `src/lib/attendancePolicy.js`, but a repository-wide search found no consumer of `attendancePolicy` outside those settings/model paths. Likewise, the salary-slab editor persists `incomeTaxPercent`, but no visible payroll calculation references that field beyond the editor and payload shape. Treat both as configuration-to-calculation gaps, not as permission to change payroll behavior without validated rules and regression tests.

## Prioritized recommendations

1. **Keep the delivered privacy safeguard and plan an authorization review.** The default masking and deliberate reveal are in this branch. Separately map roles to employee fields and Firestore access before redesigning rules; the current catch-all is broader than the UI’s module permissions. Security-rule changes need emulator tests and should not be mixed casually into a visual pass.
2. **Close the policy-to-calculation gap before expanding payroll behavior.** Document the accepted attendance policy and tax requirements, trace the calculation paths, then connect configuration only with clear ownership, historical-period rules and regression coverage. Do not infer current Indian statutory liability from a percentage field.
3. **Complete lifecycle continuity.** Decide whether hiring ends at “Hired” or should create a pre-boarding employee record, checklist, documents and start-date tasks; then define offboarding, clearance, final settlement and account deactivation. Preserve the ATS and existing employee record flows while adding the chosen handoff.
4. **Make document storage and engagement actions explicit.** If HR documents need confidential storage or retention, add a permissioned upload/version/expiry model rather than treating arbitrary URLs as managed files. Wire “Support” and “Reply” to real, permission-aware actions (or clearly disable them until a target workflow exists) without removing the current engagement content.
5. **Continue cross-device navigation and design consistency.** The missing primary routes are now connected. A follow-up should validate tile ordering and keyboard/screen-reader behavior on small screens, make active state and labels consistent, and converge visual primitives incrementally instead of replacing the existing module-specific designs wholesale.
